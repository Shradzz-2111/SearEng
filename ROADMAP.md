# ESCI Ranking Project: Roadmap

Two-stage product search ranking on the Amazon Shopping Queries Dataset (ESCI, reduced version).
Target: a working, explainable system on the resume by week 8.

This file tracks **what we build**. Repo facts and decisions live in [`docs/`](docs/README.md). Concepts, resources, and quizzes live in the Notion Learning Hub.
Keep each piece of information in one place only, so nothing goes stale.

---

## Rules

1. **A phase is done only when its tasks are merged to `main` and both of us pass the phase quiz from memory** (at least 80%, no notes).
2. **AI-generated code is allowed, unexplained code is not.** Before merging any PR, the author can explain every function in it, and the reviewer asks at least one "why" question.
3. **Write these by hand, without generating them:** the ranking metrics, the bootstrap CI, and the PyTorch training loop. They are the most likely interview topics.
4. Every PR description ends with one line: `Learned: ...`
5. The eval harness and data splits are frozen after Phase 1. Changing them requires agreement from both of us, because every later number depends on them.
6. When time runs short, cut scope using the cut line below. Do not move the deadline.

## Phase 0: Setup, data, stats basics (week 1)

**Goal:** a reproducible repo with clean, leak-free splits and a clear picture of the data.

- [ ] Repo with `pyproject.toml`, pinned dependencies, and a `Makefile` (`make data`, `make eval`)
- [ ] Download script for the ESCI data (reduced version, small_version = 1)
- [ ] EDA notebook: label distribution, query length, products per query, locale split
- [ ] Decide scope: English locale (`us`) only, or all locales. Document the decision.
- [ ] Train / val / test split **by query**, saved as versioned files with a fixed seed
- [ ] GitHub Projects board and Notion Learning Hub set up

**Definition of done:** `make data` recreates identical splits from scratch, and the EDA notebook answers "what does the label distribution look like and why does it matter?"

---

## Phase 1: Ranking metrics, BM25, eval harness (weeks 1–2)

**Goal:** a trusted evaluation harness and a baseline every later model must beat.

- [ ] Gain mapping chosen and documented (for example E=1.0, S=0.1, C=0.01, I=0, as in the ESCI paper)
- [ ] Hand-written NDCG@10, MRR, Precision@k, Recall@k
- [ ] Unit tests comparing each metric against hand-computed toy examples, including the all-irrelevant query edge case
- [ ] Bootstrap confidence intervals, resampling queries (not pairs)
- [ ] BM25 baseline over product title (and optionally brand, description)
- [ ] Two eval modes: (a) re-ranking the graded candidates, (b) full-catalog retrieval with Recall@100
- [ ] Results table in `results/RESULTS.md`, generated by `make eval`

**Definition of done:** one command reproduces the BM25 numbers with CIs, and the metric tests pass.

## Phase 2: Dense and hybrid retrieval, LightGBM ranker (week 3)

**Goal:** show that semantic retrieval and learned ranking improve over BM25, with statistical evidence.

- [ ] Product embeddings with a sentence-transformers model, stored in pgvector with an HNSW index
- [ ] Dense-only retrieval evaluated in both modes
- [ ] Hybrid retrieval with Reciprocal Rank Fusion (BM25 + dense)
- [ ] Paired bootstrap or paired test: hybrid vs BM25, with p-value and CI reported
- [ ] LightGBM LambdaRank model on hand-built features (BM25 score, cosine score, token overlap, lengths, brand match)
- [ ] Feature importance plot and one ablation (remove the strongest feature, re-evaluate)
- [ ] FastAPI `/search` endpoint returning BM25 and hybrid results

**Definition of done:** results table shows BM25, dense, hybrid, and LightGBM with NDCG@10 and CIs, all reproducible from `make eval`.

---

## Phase 3: Cross-encoder in PyTorch, ONNX (weeks 4–5)

**Goal:** a trained reranker, exported for fast inference, with measured latency.

- [ ] Decide compute before starting (Colab, Kaggle, or cloud GPU). A laptop CPU is too slow for full training.
- [ ] Hard negatives mined from hybrid retrieval candidates
- [ ] Hand-written training loop: batching, loss, optimizer, LR schedule, gradient clipping
- [ ] Checkpoints saved; early stopping on validation NDCG@10
- [ ] Evaluated in re-ranking mode against LightGBM
- [ ] ONNX export with parity check against PyTorch outputs (max absolute difference within a set tolerance)
- [ ] Latency benchmark on CPU: batch size 1 and 32, reporting p50 / p95 / p99

**Definition of done:** the cross-encoder beats LightGBM on validation NDCG@10, or there is a written explanation of why not, plus an ONNX model and a latency table.

---

## Phase 4: PySpark feature pipeline, batch scoring (week 6)

**Goal:** show the feature pipeline pattern used at scale.

- [ ] PySpark job (local mode) that builds the Phase 2 feature table
- [ ] Parity check: Spark output matches the pandas output on a sample of about 1K queries
- [ ] Batch scoring of all test candidates, written to Parquet
- [ ] Short note in the README on how this would run on a cluster (partitioning, broadcast joins)

**Definition of done:** the Spark job reproduces the pandas features within tolerance, and batch scoring runs end to end.

---

## Phase 5: Serving, Docker, Kubernetes, MLOps (week 7)

**Goal:** a deployable two-stage service with measured latency and basic monitoring.

- [ ] Two-stage endpoint: hybrid retrieval, then ONNX cross-encoder rerank of the top N
- [ ] Per-stage timing and a written latency budget (for example: retrieval 30 ms, rerank 120 ms)
- [ ] Docker image with cached dependency layers; runs with one `docker run`
- [ ] Load test (Locust or k6) reporting p50 / p95 / p99 under concurrency
- [ ] MLflow: experiments logged, models registered with versions linked to metrics
- [ ] Prometheus metrics: request count, latency histogram, error count
- [ ] Kubernetes on kind: Deployment, Service, readiness and liveness probes, HPA, one tested rolling update
- [ ] Drift check: PSI on two input features and on the score distribution, with a threshold and a log alert

**Definition of done:** `docker run` serves the two-stage endpoint, the load test is reproducible, and the README documents the latency budget against measured numbers.

---

## Phase 6: Experiments and write-up (week 8)

**Goal:** turn the system into a convincing, honest story.

- [ ] Paired significance tests for all main comparisons, with a multiple-comparison correction (Holm)
- [ ] Power analysis: queries needed to detect a 1-point NDCG@10 gain
- [ ] Interleaving simulation (team-draft) with simulated clicks from labels
- [ ] LLM reranker vs cross-encoder on about 200 queries: NDCG@10, p99 latency, cost per 1K queries
- [ ] Failure analysis: at least 10 bad rankings grouped by cause
- [ ] README: architecture diagram, results table, latency table, limitations, how to reproduce
- [ ] 3–5 minute demo video

**Definition of done:** a stranger can clone the repo, run one command, and reproduce the main results table.

## Cut line

**Must-have before applying:** Phases 0–3, the FastAPI + Docker two-stage endpoint with a latency table, the README with results, and paired significance tests.

**Cut first, in this order:** OpenTelemetry tracing → interleaving simulation → full Kubernetes setup (keep one working kind manifest) → Spark beyond a small local job → LLM reranker beyond 200 queries.

## Cadence

- **Weekend sync (30 min, fixed slot):** demo what shipped, check definitions of done, take the phase quiz together, plan next week.
- **Midweek check-in (async, 3 lines):** done / blocked / hours planned.
- **Blocked for more than a day:** say so in the check-in. Don't wait for the weekend.
- **Stuck for two days on one problem:** write down what you tried, then ask for help or move on.
- **Falling behind for two sprints in a row:** re-split the work and apply the cut line. Don't silently absorb the other person's tasks.
